//! whether it or a Windows build comes first. No runtime code in this slice.

# Design: Windows sandbox scope gate (T49.2)

## Problem

Two zeros. A Windows user today gets **zero confinement**: D7 says "Windows:
no sandbox, loud warning, `on-request` forced", and `cox_sandbox::sandbox::backend`
returns `None` on every host that is neither macOS nor Linux. And cox ships
**zero Windows binaries**: `dist-workspace.toml` targets
`aarch64-apple-darwin` (macOS is Apple Silicon only), `x86_64-unknown-linux-gnu`
and `aarch64-unknown-linux-gnu` only. So today's number of Windows users the
missing sandbox exposes is the number who build cox from source.

**Which comes first: the Windows build.** A sandbox backend nobody can
install and that no CI run exercises is untested trust code. A release target
with D7's warning and forced `on-request` is honest on day one (every
command asks), and it is what gives a backend its first test host. The
release target is out of scope here; it is a separate creator decision.

## The field

- **Codex** is the only surveyed agent with a native Windows sandbox
  (`research.md` §8.1, marked "experimental"). Elevated mode creates
  dedicated lower-privilege sandbox users, puts the filesystem boundary in
  ACLs and blocks network with firewall rules; without elevation it falls
  back to a restricted token
  (https://learn.chatgpt.com/docs/windows/windows-sandbox, redirected from
  https://developers.openai.com/codex/windows, checked 2026-09-28 — as
  recorded in the P49 card; not re-fetched for this doc). Source:
  `openai/codex` `codex-rs/windows-sandbox-rs`
  (https://github.com/openai/codex/tree/main/codex-rs/windows-sandbox-rs,
  checked 2026-09-28 per the card). **Commit not pinned**: this pass made no
  network call, so no commit was read; whether the unelevated fallback
  blocks network at all is **unverified**.
- **Microsoft AppContainer**: a process runs with its own SID and gets only
  the capabilities it is granted, including network ones
  (https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation,
  checked 2026-09-28 per the card). That an AppContainer child can be given
  write access to exactly the workspace by adding its SID to the directory's
  ACL, and that a shell such as `cmd`/`pwsh`/Git Bash runs usefully inside
  one, is **unverified** (lead: the same page and its linked
  "Implementing an AppContainer" docs).
- `research.md` §8.2: Windows image paste, sandbox and MCP install are the
  weakest area for everyone.

## cox

**Entry point.** A new `Backend::WindowsToken` (restricted token + ACLs,
unelevated) and, if the creator wants the elevated path, a
`Backend::WindowsAppContainer`, selected in `cox_sandbox::sandbox::backend`
and wrapped in `cox_sandbox::sandbox::command` next to Seatbelt, bwrap and
Landlock. `Policy` stays the single guard: `bash` calls `command` directly
(`crates/cox-tools/src/bash/mod.rs`), and every host-spawned process — stdio
MCP servers, a plugin's `[[mcp]]` servers and external agents, `doctor`'s
probe — goes through `cox_session::sandbox`'s argv wrap over the same
`command`, so none of those callers change. That wrap refuses a server on a
host with no backend or with Landlock (no argv can carry a pre-exec hook),
so today a Windows user's stdio MCP servers do not start at all outside
`danger-full-access`. The Windows backend therefore has to be an **argv
wrap**, not a spawn hook: cox itself re-launched as a small hidden
subcommand that creates the restricted child and relays its stdio, the way
`sandbox-exec` and `bwrap` wrap argv today. Whether std's `Command` can
start a process in an AppContainer without such a helper is **unverified**
(lead: `std::os::windows::process::CommandExt::raw_attribute`, stability not
checked).

**Crate.** `windows-sys` (raw Win32: `CreateRestrictedToken`,
`CreateProcessAsUserW`, the ACL and AppContainer profile calls) over
`windows`: the backend is a handful of FFI calls in one crate, and both are
listed in `rust.md` (`windows` for slint-skia-ffi, `windows-sys` for rtok's
`rtok-sys`). Both are already in `Cargo.lock` as transitive dependencies
(`windows` 0.62.2, `windows-sys` 0.52.0 and 0.61.2, read 2026-09-29); a
direct dependency is `cfg(windows)`-only and stays inside `cox-sandbox` (D1:
platform-gated dependency).

**Policy mapping.**

| `SandboxPolicy` field | Restricted token | AppContainer |
|---|---|---|
| `read-only` / `workspace-write` roots | deny-write ACEs outside the workspace are not possible without touching the user's files; a restricted token only narrows what the user can already do — weak | grant the container SID write on the workspace and `writable` roots only |
| `readonly_in_workspace` (`.git`, `.cox`) | explicit deny-write ACE for the token's restricting SID | leave the container SID without write on those two |
| `network = false` | no network control in the token itself — needs Windows Filtering Platform or firewall rules (elevation) | omit the network capabilities |
| `danger-full-access` | bare command, as today | bare command, as today |

Until a backend lands, D7 stands unchanged: `backend` returns `None`, the
session shows the security notice and `on-request` is forced. No second guard:
`cox_permission::Engine` keeps deciding every call, and
`cox_sandbox::path::confine` keeps confining model paths with
`std::fs::canonicalize`; whether it is correct on Windows `\\?\` and
drive-relative paths has never run on a Windows host (**unverified**) and is
the first test a Windows CI job would run.

## Falsifiers

1. Elevated setup (sandbox users, firewall rules) is blocked on managed
   machines, leaving only a restricted token whose network and
   out-of-workspace write control is weaker than D7's forced `on-request` —
   then shipping it would *lower* safety by relaxing the forced prompts, and
   the answer is to keep D7.
2. No Windows release target exists by the time the backend is ready — then
   it ships to nobody and rots untested.
3. AppContainer cannot run the shells users need (Git Bash, `pwsh`) with
   workspace access — then only the token path remains; see 1.

## Review

**Recommended verdict: defer** — pending the creator's decision. Order: a
Windows release target first (its own decision, out of scope here), with D7
unchanged; then this backend, AppContainer-first if falsifier 3 does not
fire, never a token-only backend that relaxes D7's forced `on-request`. If
the creator chooses **build**, the §6 amendment draft is: (1) Windows
target in `dist-workspace.toml` plus a Windows CI job for `cox-sandbox`
and `path::confine`; (2) `Backend::WindowsAppContainer` behind `command`
with the mapping above; (3) `cox doctor` reporting it. The D7 Windows line
changes only when (2) is approved.

**Creator's verdict (2026-09-29, `plan.md` A123): defer.** A Windows release target comes first, as its own decision; there is never a token-only backend that relaxes D7.

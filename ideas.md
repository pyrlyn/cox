## Build system

- Buck2 or Bazel instead of cargo + XcodeGen (raised by the creator on 2026-10-07, not approved). What they would add: a remote action cache and remote execution shared by CI, worktrees and machines; one build graph for Rust and Swift (rules_rust, rules_swift/rules_apple or rules_xcodeproj; Buck2's prelude), so the XCFramework stops being a separate step; hermetic, input-keyed caching. Why not now: they do not make rustc or the linker faster, and cox's main suspected costs, not measured yet (fat-LTO link, 79 integration-test binaries, the workspace compiled twice per CI target) are inside rustc and the linker, which P60 addresses directly; incremental compilation inside a crate is off by default in rules_rust (**unverified**, check the rules_rust docs before relying on it), so the local edit-build loop could get slower; the migration covers BUILD files for 35 crates and every third-party crate (crate_universe or reindeer), the build scripts (typify, `cox-plugin-fixtures` running cargo for wasm32, whisper.cpp through cmake, uniffi), nextest, insta, trycmd, `CARGO_BIN_EXE_*`, cargo-dist, release-plz, cargo-deny/audit, dependabot, rust-analyzer (`rust-project.json`), XcodeGen and the mise pins, plus every cargo command in `AGENTS.md`; remote execution needs a service (BuildBuddy, EngFlow, NativeLink) or own infrastructure. The cheaper path to the shared cache is P60's sccache (T60.7) and CI caches (T60.4), and sccache with a remote backend (S3, Redis, GitHub Actions cache) if machines multiply. Revisit when P60's `research.md` §4.3.9 numbers show CI or agent time still dominated by rebuilding what was already built elsewhere, or when the number of agents and machines grows enough to justify a remote cache service.
